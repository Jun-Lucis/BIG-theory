## v1.0 — 2026-06-06

**Tag:** `v1.0`  
**Original release title:**  
`BIG Numerical Series v1.0 Discovery → Universality → Classification`

This release is a **historical snapshot of the early numerical boundary-layer phase**. It covers:

- BIG-B3.1 — boundary-layer scaling and quadratic landing;
- BIG-B4.1 — parameter scans of the approximate quadratic landing exponent;
- BIG-B4.3 — stability/compression classification under joint parameter variation.

The term **“Universality”** in the original release title referred to the then-tested robustness of the approximately quadratic local landing exponent within that restricted B3/B4 numerical family.

It should **not** be read as the current programme-level claim that all BIG sectors share one universal quantitative law.

Subsequent work materially narrowed the universality claim:

- B19 did not find a robust tested ray-independent upstream scalar collapse;
- B23A prospectively separated structural/formal universality from quantitative universality;
- B24 indicated multiple native boundary classes rather than one pre-existing common operator;
- B26 validly identified a geometry-transfer failure for the tested fixed-coefficient perimeter closure.

The current repository-level synthesis is therefore:

> **BIG provides a common formal language for comparing system-dependent boundary geometry, response, history, branch structure, and reconfiguration. Current evidence does not establish one universal numerical boundary law across the programme.**

## Current release practice

Later scientific outputs are primarily archived as **Zenodo publications with DOI**, with GitHub used for:

- repository-level navigation;
- living documentation;
- paper-entry summaries;
- status maps;
- citation guidance;
- reproducibility-oriented source organization.

If a future GitHub Release is created as a current repository snapshot, its title and body should preserve the distinction between:

```text
structural / formal comparability
    !=
programme-wide quantitative universality
```

and should link back to the integrated status map rather than restating one selected positive result as the state of the whole programme.
